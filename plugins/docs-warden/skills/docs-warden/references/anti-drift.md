# Anti-drift

Scaffolding is a one-day win. Drift is the thing that actually costs you, and the
only reliable defence is machine enforcement in CI. Everything here exists to make
"the docs are wrong" a red build rather than a discovery six months later.

## The load-bearing idea

**Anything that can be generated is generated, and CI regenerates it and fails on a
non-empty diff.**

A generated file that a human *can* hand-edit *will* be hand-edited, usually in a
hurry, usually correctly, and after that the generator is broken and nobody knows.
So every generated document declares itself in its first line:

```text
<!-- GENERATED by docs-warden - do not edit -->
```

and appears either in `generated_docs` in `.docs-warden.yml` or in the index check.

A document that is only *partly* generated (a table inside an otherwise
hand-edited README, for example) cannot carry that whole-file marker without
lying about the rest of the file. Bracket the generated region instead, with a
name so more than one region can coexist in one document:

```text
<!-- BEGIN GENERATED:<name> - run <command to regenerate> -->
...
<!-- END GENERATED:<name> -->
```

The region still belongs in `generated_docs`. The check restores whatever the
file held before it ran, not a known-good version: it verifies, it never
repairs. A generated document that was already stale when the audit started is
reported and left exactly as stale. What changes is linting: a fully generated file
is exempt from prose style (see `assets/lint/.vale.ini`), a partly generated
one is not — the hand-written prose around the region still needs it.

## Ownership

`CODEOWNERS` puts the `owner` from `.docs-warden.yml` on `docs/` and the root
documents. Without a named reviewer, documentation changes get rubber-stamped by
whoever is nearest.

`review_by` front matter gives each document an expiry. `freshness.py` fails once
it passes. The point is not that the document is wrong on that date — it is that
somebody has to look.

## Freshness, two ways

1. **Calendar** — `review_by` has passed.
2. **Relative to code** — the document references a source path, and that path's
   last commit is newer than the document's. This catches the real failure mode:
   the code moved, the document did not, and no date was involved.

The second is a `warn`, not a `fail`. A doc can legitimately outlive a refactor.

## Documents in the same pull request

The PR template checkbox is the cheapest control here and the most effective:

```markdown
- [ ] Docs updated, or explicitly N/A because: ______
```

Requiring the *reason* is what makes it work. A bare checkbox gets ticked without
thought; a blank that must be filled in gets read by the reviewer.

## Linters

Three, each doing one job:

- **markdownlint-cli2** — structure. Heading increments, no bare URLs, relaxed line
  length with tables and links exempt.
- **Vale** — prose. House rules plus off-the-shelf packages. Generated documents and
  `docs/DECISIONS.md` are excluded; linting a generated file just annoys the generator's
  author.
- **lychee** — links. Checks relative and external links, accepts 429, excludes localhost and `*.internal`.

**Roll them out at warning level.** A new linter turned on at error level across
existing repos produces hundreds of findings, and the team's rational response is to
disable it. Warn first, fix the backlog, then promote to error.

Pin every tool version, and verify the pinned version actually exists before writing
it down. Do not download style packages from inside the skill; the CI workflow does
that.

Layout in the target repo: `.vale.ini`, `.markdownlint-cli2.yaml` and
`lychee.toml` at the root; Vale rule files in `styles/Clarity/`; the
generated vocabulary in `styles/config/vocabularies/Project/`. `StylesPath = styles`
in `.vale.ini` is what ties them together.

## Known gap: nothing enforces this in CI yet

`.pre-commit-config.yaml` runs the three linters locally, so prose, structure and
link findings arrive before the push. **The generated-document checks do not run
anywhere automatic.** `adr_index.py --check`, `freshness.py` and
`audit.py --run-generators` are the half that actually catches drift, and today a
human has to run them.

That is a real hole in the idea this file is built on, so it is written down rather
than papered over: a generated document can go stale between one manual audit and
the next, and nobody is told.

**The upgrade path.** The scripts ship in a public repository, so a workflow can
reach them with a second `actions/checkout` — no token, no packaging — once there is
a ref worth pinning to:

```yaml
- uses: actions/checkout@<sha>          # the repo under test
- uses: actions/checkout@<sha>          # the scripts
  with:
    repository: kuan51/claude-skills
    ref: <release tag or commit sha>
    path: .docs-warden-src
- run: pip install pyyaml==6.0.3
- run: python3 .docs-warden-src/plugins/docs-warden/skills/docs-warden/scripts/adr_index.py . --check
```

Pin to a tag or a full commit SHA, never a branch. `--run-generators` EXECUTES
commands out of the audited repository's `.docs-warden.yml`, so gate that input on
the event: true for a push or a same-repo pull request, false for a fork PR, whose
head is not trusted.

Ordering, when that workflow exists: markdownlint, then vale at warning level
(non-blocking at first), then lychee, then `adr_index.py --check` failing on a diff,
then `freshness.py`, then `audit.py --run-generators` writing `docs-scorecard.json`
as an artifact.

The scorecard artifact is what makes the cross-repo view possible: collect it from
every repo and you have one table showing which repos are actually maintained.
