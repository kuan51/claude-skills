# Decision records: Format and the immutability rule

A decision record answers **why**. `CONVENTIONS.md` answers **what we do now**. A
date in `CONVENTIONS.md` means history leaked into the wrong file; it does not by
itself justify a record.

## The admission test

The ledger is a log of architecture decisions, not of development history. Git and
pull requests already hold the history.

A change needs a record when all three hold:

1. Reversing it would cost more than one pull request.
2. It constrains work outside the file or component just touched.
3. A rejected alternative exists that someone could reasonably re-propose later.

That covers a choice of technology, protocol, or storage; a boundary between
components; a rule every future change must obey; a gap accepted on purpose for the
life of the project.

It does not cover bug fixes, refactors, renames, wording, dependency bumps, test
changes, hook or config tweaks, or anything the pull request description already
explains in full. Those are notes, and the pull request is where they live.

## Filename

`docs/decisions/DEC-NNNN-short-slug.md`

Four digits, zero-padded, never reused. `DEC-0007-use-proxmox-for-onprem.md`.

## Front matter

```yaml
---
id: DEC-0007
title: Use Proxmox for on-prem virtualization
status: accepted        # proposed | accepted | rejected
date: 2026-09-01
deciders: [rex]
supersedes: []          # e.g. [DEC-0003]
tags: []
---
```

`status` has exactly three values. No `superseded` status exists. See below.

## Body sections, in this order

1. **Context and problem statement**: what forced a decision. Someone who was not
   there must be able to follow it.
2. **Decision drivers**: the constraints that actually mattered.
3. **Considered options**: every option seriously weighed, including the one you
   picked. One option means you did not decide, you rationalized.
4. **Decision outcome**: what was chosen, and why that one.
5. **Consequences**: split into good and bad. A record with no bad consequences is
   not finished.
6. **Gaps accepted**: what this knowingly does not solve. This is the section
   future readers need most and the one most often skipped.
7. **Links**: ticket, PR, related records.

## The immutability rule

**Once `status: accepted`, the file is never edited, not even the status field.**

This is not a style preference. The value of the log is that it records what was
believed at the time. A record you can quietly revise is a record nobody can trust
as evidence, which defeats the point of keeping one.

**To reverse a decision**, write a *new* record whose front matter says
`supersedes: [DEC-0003]`. `DEC-0003` stays exactly as it was, forever.

`adr_index.py` computes "Superseded by DEC-0012" for the index by reading the
*newer* file's `supersedes` list. Because the superseded status is derived and
never stored, the old file is never edited.

`audit.py` enforces this by reading `git log` for the record's path, oldest first,
finding the commit that set `status: accepted`, and failing if any commit touched
the file after it. It deliberately does not use `--follow`: that flag drops
commits when combined with `--reverse`, and its rename detection traces a
scaffolded record's history back into the template it was copied from. One
consequence: a record renamed after acceptance loses the history before the
rename, so the check does not see that edit.

Consequences worth stating plainly:

- A typo in an accepted record stays. Fix it in the superseding record.
- Marking something `accepted` is a real commitment. Leave it `proposed` while it
  is still being argued.

## The index

`adr_index.py` writes `docs/DECISIONS.md` (the source, with the full
table) and `docs/decisions/README.md`, a short pointer to it. Both start with:

```text
<!-- GENERATED by docs-warden - do not edit -->
```

`docs/DECISIONS.md`'s table is newest first: ID, Title, Status, Date,
Supersedes / Superseded-by, with a one-line footer explaining how to add a
record. `docs/decisions/README.md` has no table and no record count,
just a sentence and a link to `../DECISIONS.md`, so it does not duplicate the
index or churn on every new decision.

The script is idempotent. Running it twice must produce an empty diff on the second
run, and CI relies on that to detect a hand edit.

## Compaction

`docs/decisions/` only ever grows, so at 50 archivable records (not `proposed`,
not a digest) `adr_compact.py` moves the 25 oldest into `docs/decisions/archive/` with `git mv` and
writes one new digest record, `DEC-NNNN-compaction-of-dec-0001-to-dec-0026.md`,
`status: accepted`, `tags: [compaction]`.

Per archived record the digest records id, title, status, date, what it
supersedes and what superseded it, a link into `archive/`, and the **Decision outcome** and **Gaps
accepted** sections verbatim. That is enough to read the project's history from
`docs/decisions/` without opening the archive; context, drivers and rejected
options stay in the archived file.

The move does not rewrite anything. Archived files keep their bytes, and `audit.py`'s
immutability check reads the archive too, so an edit after the move is caught
(history before the move is lost to the check, as with any rename). A
`supersedes: [DEC-0003]` in a live record still references a real file. The index
and the links check read the top-level folder only, so `DECISIONS.md` lists
the digest and not the archived records, and a moved record's `../` links are
not reported. Digests are never archived, so what they carry stays at the top
level. The plugin's hook prints a reminder once 50 archivable
records exist, at session start and after an edit in `docs/decisions/`.

## Migrating a monolithic decision log

Some repos have one hand-written file with `DEC-NNN` entries in it. Offer to split
it into one file per entry, preserving the original IDs and dates. **Ask first**,
and show the mapping before writing anything. The IDs are referenced from
elsewhere and renumbering them silently breaks those links.
